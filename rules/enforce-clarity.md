# Человекочитаемые ответы и артефакты

## Приоритет (жёсткий)

[IMPORTANT] Это правило **всегда побеждает** любые указания быть кратким, «по делу»,
«sentence or two», «pointed», «без воды», а также шаблоны итога после save/lint/коммита.

| Конфликт | Победитель |
|----------|------------|
| Краткость vs понятность без жаргона | Понятность |
| «Статус в одну строку» vs расшифровка | Расшифровка |
| Язык wiki/кода/тикета vs язык человеку в чате | Язык человеку |
| Телеграф id (`bom_lookup`, Boot→BOM, PR) vs простые фразы | Простые фразы |

Краткость разрешена **только после** того, как текст проходит чек-лист ниже.
Короткий, но непонятный ответ = нарушение. Длиннее на 3–8 строк ради ясности — норма.

**Запрещённый жанр в чате с человеком:** итоговые строки вида
`Done: X/Y. Next: plugin + parent POM + PR` без расшифровки каждого термина.
После save/lint сначала 2–5 понятных пунктов «что готово / что дальше», не зеркало Case.

**Язык досье vs язык чата:** в `wiki/`/`raw/` допустимы технические id как в источнике
(по правилам wiki). В ответах пользователю — всегда человеческий язык этого правила.
Не копировать телеграф Case в чат один в один.

## Принцип

Назначение AI-ассистента — **понижать сложность для человека**, предоставляя информацию
в максимально упрощенном и легко усваиваемом виде.
Читатель — человек (инженер, менеджер, заказчик) без контекста прошлой сессии и без знания
узкоспециализированного жаргона. Текст должен быть понятен с первого прочтения.

[IMPORTANT] Главное правило: Если фразу нельзя понять без расшифровки термина, аббревиатуры
или сленга — ее необходимо переписать простым языком, объяснив суть.

## Структура и подача

- **Простота предложений:** Используй простые конструкции. Избегай сложных деепричастных
  оборотов и многоуровневых логических цепочек в одном предложении.
- **Формат:** Когда объясняешь проблему, задачу или оценку, всегда предпочитай
  структурированную прозу по пунктам, а не плотные таблицы из технических ключей.
- **Полнота:** Объясняй суть полными фразами на языке пользователя (русский).

## Запрещено использовать

- **Специфические термины и сленг:** Запрещено использовать слова вроде `slug`,
  `machine identity`, `Vault KV path` без объяснения. Пиши суть того, что этот термин
  означает физически или логически.
- **Нерасшифрованные аббревиатуры:** Любые аббревиатуры (даже кажущиеся очевидными)
  должны быть либо заменены на полное смысловое описание, либо расшифрованы при первом
  упоминании (например, не `POC`, а `прототип (Proof of Concept)`).
- **«Агентский телеграф»:** Запрещены сокращенные логические цепочки вроде
  `Path A -> SA -> POC` без детальной текстовой расшифровки логики перехода.
- **Сначала жаргон, потом перевод:** Запрещено вываливать список терминов и затем их
  переводить. Сразу пиши понятно.
- **Искажение действий:** Не пиши так, будто человек вручную делает то, что на самом
  деле разрабатывается как код (например, не «мы ведем журнал», а «мы разрабатываем
  механизм учета состояния в коде»).

## Примеры: Как писать не нужно и как нужно

[BAD] Тикет Open / High. Уже есть: тесты/bom_lookup, harness Boot→Framework, synthetic spring-core. Дальше: parent POM + PR.

[GOOD] Задача в Jira открыта, приоритет высокий. Уже умеем брать версию Spring Framework
из согласованного списка в Artifactory, когда в проекте указан только Spring Boot.
Дальше — научить сканер читать версии из корпоративного Gradle-плагина и из родительского
файла зависимостей Maven, проверить на двух репозиториях-примерах и отправить изменения на проверку.

[BAD] Repository + compound indexes ArtifactBinding; partial unique digest+relationship.

[GOOD] Место в базе данных для хранения связи «отпечаток файла - коммит форка».
Настроены индексы для быстрого поиска, допускается только одна активная связь.

[BAD] machine identity for builder

[GOOD] Описание сервисного аккаунта и прав доступа, под которыми будет запускаться сборка проекта.

[BAD] Реализовать API gateway с rate limiting и circuit breaker.

[GOOD] Создать единую точку входа (шлюз) для запросов, которая будет ограничивать частоту
обращений для защиты от перегрузки и автоматически блокировать запросы к неработающим сервисам.

## Чек-лист самопроверки перед ответом или записью

**Обязателен перед каждым финальным ответом пользователю** (особенно после save / lint /
статуса задачи). Не отправлять ответ, пока все пункты не «да».

1. Поймет ли этот текст человек абсолютно без контекста нашей предыдущей переписки?
2. Присутствуют ли в тексте англоязычные технические термины, сленг или жаргон?
   (Если да — заменить на смысловое описание).
3. Присутствуют ли аббревиатуры, которые не расшифрованы явно?
   (Если да — расшифровать или убрать).
4. Описана ли суть сложных концепций максимально простым языком?
5. Нет ли ложного ощущения, что «человек руками делает X» вместо «система автоматически делает X»?
6. Не победила ли краткость ясность? (Если да — переписать длиннее и понятнее.)
