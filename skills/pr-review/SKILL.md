# Ревью pull request

Только Critical и High, пока пользователь не расширил уровни. Security-аудит и отправка review на GitHub - только по явной просьбе.

## Процесс
1. Собрать улики: diff, скрины, описание pull request, задача в Jira. Чего нет - не додумывать.
2. Сверить title и задачу со списком файлов. Чужое игнорировать.
3. Комментировать только новое или изменённое поведение этого pull request. Перенесённый старый код без смены смысла - не слать.
4. Перед Critical/High сверить с актуальным кодом или последним скрином.
5. Сохранять ревью в wiki / базу знаний только по просьбе «сохрани / закрой ревью».

## Приоритеты
- **Critical** - ломает основной путь: падение, порча данных, решение не по задаче.
- **High** - ломается при обычном использовании в проде, но не на основном пути.
- Ниже High (Medium / Low / Nit) в этом режиме не репортить. Сомнение в уровне - спросить. Редкий путь при верном основном - не выше Medium (значит не в выдачу по умолчанию).

## Формат замечания
- **RU:** проблема / влияние / файл:строки / как исправить (с кодом при необходимости). Простым языком.
- **EN (по умолчанию; для слабой модели или по просьбе - только по запросу):** `file:lines` - problem; impact; fix. Кратко, вежливо.

Номера строк - только со скринов или diff. Не видно - так и написать.

После замечаний: **Summary** (EN) + вердикт; **Teams** - 1-2 предложения EN. Если Critical/High нет - сказать явно.

## Вердикт (предложение; решает пользователь)
- Critical → Request changes
- High → Request changes или Comment (уточнить)
- Нет Critical/High (или High принят как non-blocking) → Approve
