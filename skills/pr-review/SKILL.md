# Ревью pull request

Узкий фильтр по серьёзности, понятные объяснения на русском, готовые английские тексты для GitHub.

**Делает:** разбор diff/скринов/Jira; замечания по приоритету (RU для пользователя + EN для автора); summary PR; короткий Teams; предлагает вердикт Approve / Comment / Request changes.

**Не делает:** глубокий security-аудит (skill `security`); замечания без улик; придирки к перенесённому коду без изменения смысла; отправку review на GitHub без явной просьбы.

## Процесс

1. **Улики** — собрать скрины кода, diff, описание PR и Jira. Чего нет в уликах — не додумывать («в данных нет»).
2. **Scope** — сверить title PR/Jira со списком файлов. Скрины и файлы, не относящиеся к Jira/PR, игнорировать.
3. **Отбор** — только Critical и High, пока пользователь не попросил другие уровни. Сомнение в уровне → спросить пользователя.
4. **Выдача** — по формату ниже.
5. **Закрытие** — только по «сохрани / закрой ревью»: сохранить в wiki/KB по правилам базы знаний.

## Приоритеты

- **Critical** — ломает основной путь: падение, некорректные или испорченные данные, решение не соответствует задаче Jira.
- **High** — ломается при обычном использовании в проде, но не на основном пути (реалистичный ввод, типичный edge case, исключение).
- **Medium** — хрупкость при следующем изменении или редкий путь; тест закрепляет слабый контракт.
- **Low / Nit** — стиль; unused import без доказанного падения CI; чужой UI/lockfile → «лучше отдельным коммитом».
- **Не слать** — перенесённый старый код; спор о смысле, если на happy path поведение уже верное.

**Понижение:** проблема только на редком/историческом пути, а основной путь корректен → максимум Medium.

## Формат выдачи

Для каждого замечания:
- **RU (для пользователя, простым языком, без жаргона):** в чём ошибка (при необходимости — алгоритм по шагам); влияние (что сломается для пользователя, данных или следующего изменения); файл и строки; как исправить, с примером кода.
- **EN (для GitHub):** `file:lines` — проблема, влияние, предлагаемое исправление. Кратко, вежливо, готово к копированию.

Номера строк брать со скринов/diff. Если строка не видна — так и написать, не угадывать.

После замечаний:
- **Summary PR** (EN) и предлагаемый вердикт;
- **Teams** — 1–2 коротких предложения, EN.

Если Critical/High нет — сказать об этом явно.

## Вердикт

- Есть Critical → Request changes.
- Есть High → Request changes или Comment (уточнить у пользователя).
- Critical нет, High нет или принят как non-blocking → Approve (замечания — комментариями).

Вердикт — предложение, решает пользователь.

## Фильтры

- Комментировать только новое или изменённое поведение этого PR.
- Нерелевантный FAQ/README/код в фичевом PR → Nit, не High.
- Перед отправкой Critical/High сверить с актуальным кодом (скобки, последний скрин), а не со старой гипотезой.
- Не раздувать High и ревью в целом; не добавлять Low/Nit в проходе «только Critical/High».
